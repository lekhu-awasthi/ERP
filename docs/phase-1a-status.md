## Bugs hit and fixed along the way

1. **XML comment `--` bug again** (same class as Phase 0's item 3): a `<!-- DbSet<T> ... -->` comment in `ErpApp.Application.csproj` broke project parsing. Fixed by avoiding `<T>`-shaped `--` runs in comments generally.
2. **NuGet package downgrade error (NU1605)**: adding `Microsoft.Extensions.Identity.Core` at its latest patch (`10.0.10`) conflicted with several packages explicitly pinned at `10.0.0` elsewhere in the solution. Fixed by bumping all `Microsoft.Extensions.*`/EF Core packages solution-wide to `10.0.10` for consistency.
3. **EF Core InMemory provider vs. `rowversion` concurrency token**: `User.RowVersion` (`byte[]`, non-nullable per NRT) made the InMemory test provider treat it as a required column and throw on insert, since InMemory has no equivalent of SQL Server's store-generated `rowversion`. Making the CLR property nullable broke the real SQL Server migration instead (`rowversion` columns can't be nullable in SQL Server — `ALTER COLUMN` was rejected). Fixed by keeping the domain/DB model as-is and excluding `RowVersion` from the **test-only** EF model (`modelBuilder.Entity<User>().Ignore(...)`) in `TestAppDbContext`.
4. **JWT bearer's default inbound claim mapping**: `ClaimsPrincipal.FindFirstValue(JwtRegisteredClaimNames.Sub)` (used by `/me`) returned `null` even for a valid token, because the handler remaps `"sub"`/`"email"` to long legacy XML-namespace claim types on the way in by default. Fixed with `options.MapInboundClaims = false;`.
5. **Cross-scheme cookie `SameSite=Lax`**: the Angular dev server (`http://localhost:4200`) and Api (`https://localhost:7104`) differ only in scheme, but Chrome's schemeful-same-site treats that as cross-site — `SameSite=Lax` silently dropped the `erp_auth` cookie on every cross-origin fetch. Fixed with `SameSite=None` (paired with the already-required `Secure`).
6. **Logout didn't clear the session**: `Response.Cookies.Delete(name, new CookieOptions { Path = "/" })` didn't match the original cookie's `Secure`/`SameSite` attributes, so browsers silently ignored the delete and `/me` kept succeeding after "logout". Fixed by matching `HttpOnly`/`Secure`/`SameSite`/`Path` exactly between the `Append` (login) and `Delete` (logout) calls.
7. **TestSprite's tunnel prober vs. HTTPS-only Kestrel port**: TestSprite's backend-test tunnel connects but never completes a TLS handshake against the HTTPS-only port (`:7104`); Kestrel just drops the connection ("socket hang up"), regardless of dev-cert trust. Worked around **temporarily** for that one test run by disabling `UseHttpsRedirection()` and pointing TestSprite at the plain-HTTP port (`:5155`) instead — reverted immediately after, confirmed HTTPS-redirect behavior restored.
8. **Eager vs. lazy configuration reads breaking `WebApplicationFactory`-based tests (the big one)**: `Program.cs` read `Jwt:SigningKey` via `builder.Configuration.Get<JwtOptions>()` into a local variable *before* the host finished building, then closed over that stale snapshot inside `AddJwtBearer(...)`. `WebApplicationFactory`'s test-only config overrides (`ConfigureAppConfiguration`) are chained in later, during `.Build()` — too late for that snapshot to see them. Since `UseAuthentication()` initializes `JwtBearerOptions` on *every* request (not just ones requiring auth), a plain `GET /health` threw `ArgumentNullException` on a null signing key — caught by the exception handler and returned as an opaque 500 with no clue in the response body why. **The exact same eager-read pattern already existed (since Phase 0) in `Infrastructure/DependencyInjection.cs` for `ConnectionStrings:Default`**, masked in CI by the workflow's env var arriving early enough via `CreateBuilder()`'s own environment-variable provider, and masked locally by my own already-present `dotnet user-secrets`. **Root-caused by temporarily moving `secrets.json` aside** to simulate a truly clean checkout — only then did both failures reproduce locally. **Fixed both** by deferring the reads to first actual use: `Jwt:SigningKey` via `IOptions<JwtOptions>` injected into `AddOptions<JwtBearerOptions>().Configure<IOptions<JwtOptions>>(...)`, and the connection string inside `AddDbContext`'s lazy options delegate.
   - **General rule for Phase 1b onward**: never do `builder.Configuration.Get<T>()` (or `.GetConnectionString(...)`, `.GetSection(...).Get<T>()` etc.) as a **top-level statement in `Program.cs`, evaluated before `.Build()`**, if the resulting value gets captured into a closure that runs later (an options-configure delegate, a DbContext options builder, etc.). Prefer `services.AddOptions<T>().Bind(configuration.GetSection(...))` (lazy — `IConfigurationSection` is a live view) or resolve `IOptions<T>`/`IConfiguration` from the `IServiceProvider` inside a lazily-invoked delegate. This is *exactly* the trap that made Api.IntegrationTests silently rely on developer-machine user-secrets to pass, instead of testing what it claimed to test.
9. **`gh` (GitHub CLI) wasn't installed** — needed to fetch the actual CI failure detail (the Api's exception handler deliberately doesn't leak exception info into HTTP responses, so the real stack trace only exists in the CI job's raw log / the uploaded TRX artifact's captured stdout, neither of which is visible from the GitHub web UI's summary view or a plain `WebFetch` — GitHub's Actions log/artifact endpoints require authentication). Installed via `winget install --id GitHub.cli`; was already authenticated via existing credentials.

## Tooling notes for future sessions

- **`gh` CLI is now installed** (`C:\Program Files\GitHub CLI\gh.exe`) and authenticated as `lekhu-awasthi`. Bash's `PATH` wasn't refreshed after install this session — invoke via the full path, or open a fresh shell.
- **Debugging a CI-only failure**: `gh run view <run-id> --repo lekhu-awasthi/ERP --job <job-id> --log` gets the raw log, but for a failing xunit test specifically, `gh run download <run-id> --repo lekhu-awasthi/ERP --name dotnet-test-results --dir <dir>` and reading the `.trx` XML's `<StdOut>` element is more reliable — it captures full console output (including `fail:`-level framework logs) that the summarized `--log` view can truncate/reorder.
- **Real email**: `Email:*` (SMTP via Gmail, port 465 implicit TLS, MailKit) is configured via the user's own `dotnet user-secrets` — never committed. A fresh clone needs `Email:From`/`SmtpServer`/`Port`/`Username`/`Password` set (see `appsettings.Development.json`'s placeholder comment for the exact commands) before the Api will start at all (`ValidateOnStart()`).
